# Load tests

Load tests for go-router, driven by [vegeta](https://github.com/tsenart/vegeta).

They exist to answer a question the unit tests cannot: the router swaps its
tree atomically and decodes segments lazily so that serving stays cheap and
lock-free. Those are claims about behaviour *under concurrent load*, and only
load can check them.

## Why a separate module

`loadtest/go.mod` is its own module, with a `replace` back to the parent.
Vegeta and its transitive dependencies are a test harness; someone importing
go-router should not inherit them. The root module still requires nothing but
testify.

## Running

The suite drives vegeta as a library, so it needs no binary and no port
juggling — `go test` is enough:

```sh
cd loadtest
go test ./...            # every scenario, default rate
go test -race -v ./...   # with the race detector and the per-scenario numbers
go test -short ./...     # skip the load tests entirely
```

Tunable, for a soak run or for a slower machine:

| variable | default | meaning |
|---|---|---|
| `LOADTEST_RATE` | `2000` | requests per second per scenario |
| `LOADTEST_DURATION` | `2s` | how long each scenario attacks |
| `LOADTEST_WORKERS` | `50` | vegeta workers |
| `LOADTEST_P99` | `250ms` | p99 budget each scenario asserts |

```sh
LOADTEST_RATE=20000 LOADTEST_DURATION=30s go test -v -timeout 30m ./...
```

## What each scenario pins

Every scenario isolates one decision the tree makes, so a regression names
itself instead of being averaged away. All of them assert on **every** hit —
not on a sample — that the status, the response body and the headers are what
the route promised. A load test that only measured throughput would pass just
as happily against a router that answered fast and wrong.

| scenario | what it covers |
|---|---|
| `StaticRoute` | depth-1 static hit, the baseline every other row is read against |
| `SingleParameter` | one capture, and that the bound value is the right segment |
| `NestedParameters` | parameter → static → parameter, the walk that leaves and re-enters static children |
| `StaticBeatsParameterUnderLoad` | precedence between a static route and a parameter route that both match |
| `MiddlewareChain` | a two-level group and a five-layer `With` stack, order asserted via `X-Chain` |
| `MountedSubtree` | a grafted router keeping its handlers and middleware |
| `NotFound` | the full failed walk: unknown paths, prefixes of real routes, one segment past one |
| `MethodNotAllowed` | 405 plus the rendered `Allow` header, which is string building on the hot path |
| `HeadFallsBackToGet` | HEAD with no route of its own, which costs a second lookup |
| `OptionsAnsweredAutomatically` | 204 + `Allow`, answered by the router rather than a handler |
| `PercentEncodedSegments` | per-segment decoding: `%2F` stays inside one variable |
| `MixedTraffic` | all of the above interleaved on one tree |
| `RegistrationWhileServing` | routes registered mid-attack; in-flight traffic never sees a half-built tree |
| `MountWhileServing` | the same for `Mount`, which swaps a whole subtree at once |
| `ShapeComparison` | the same rate against each route shape, reported side by side |

### Burst scenarios

The scenarios above are *paced*: a fixed rate against a small, hand-written set
of routes. The burst scenarios are the other half — a full route table, hit all
at once with no pacing at all.

Unpaced is a different test, not just a faster one. At a fixed rate the harness
decides when the next request goes out, so the router is never what sets the
pace; with the pacer removed, every worker sends its next request the instant
the previous answer lands, and the tree is what the throughput measures.

The table they run against is generated by `app.Catalog()`: three API versions
as nested groups, eight resources each, sub-collections under a parameter, a
static sibling next to every `{id}`, and three mounted subtrees — **249
routes**. The route list, the registrations and the expected answers all come
from that one function, so a route that exists but is never hit is impossible
by construction.

Every handler answers with the pattern it was registered under plus the
variables it bound, and the expectation is computed by an independent second
walk of the pattern and the request. That is what makes the burst worth
running: under a wide tree at full tilt the failure worth catching is not a
slow response but a request landing on a neighbouring node, or on the right
node with the wrong segment bound. Both show up as a body mismatch.

| scenario | what it covers |
|---|---|
| `EveryRouteInTheTable` | all 249 routes, unpaced, every hit's body verified, and a route the burst never reached fails the test |
| `ColdTree` | a burst with no warm-up at all: correct from the first request, not from the hundredth |
| `Spike` | idle trickle, then a jump straight to full rate on fresh connections |
| `Ramp` | 1k → 40k/s in steps, reported as a curve so you can see where latency bends |

| variable | default | meaning |
|---|---|---|
| `LOADTEST_BURST_WORKERS` | `200` | connections the burst is capped at |
| `LOADTEST_BURST_DURATION` | `3s` | how long the unpaced scenarios run |

`burstWorkers` caps `MaxWorkers` deliberately. Left unbounded, an unpaced
attack spawns a worker per outstanding request and ends up measuring how many
goroutines the *generator* can hold rather than how fast the router answers.

`ShapeComparison` asserts nothing about the absolute numbers — those belong to
the machine. What is worth reading is the distance between the rows, which is
where the cost of a parameter, a decode or a middleware layer shows up.

## The vegeta CLI

For longer runs, higher rates, driving from another machine, or vegeta's own
reporters (histograms, HDR plots, JSON for a dashboard):

```sh
go install github.com/tsenart/vegeta/v12@latest

./run.sh                        # every target file at 5000/s for 10s
RATE=20000 DURATION=30s ./run.sh
./run.sh mixed static           # only these
```

`run.sh` builds and starts `cmd/loadserver`, waits for the socket rather than
sleeping a guessed amount, runs each file in `targets/`, and leaves the raw
results, a JSON report and an HTML plot in `results/`.

The server can also be driven by hand:

```sh
go run ./cmd/loadserver -addr :8080
vegeta attack -targets=targets/mixed.txt -rate=10000 -duration=30s | vegeta report
```

`cmd/loadserver` and the in-process suite build their routing tables from the
same `app.New()` / `app.NewCatalog()`, so a number measured through one is a
number about the other. On `^C` the server prints how many requests reached a
handler, which is the cheapest cross-check that its count and vegeta's agree.
